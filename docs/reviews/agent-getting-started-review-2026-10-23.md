## P1：发布前应解决

### A01：安全保证与实际交付截图直接冲突

**原句摘录（第 52、89、97 行）**：“这类需求说清楚的情况下一般不会出事”；“用本文给的提示词，一路点下去不会出事”；alt 将交付说明概括成“主动说明 jsdom 安装失败的原因”。

**问题**：直接查看 `06-result.webp`，左侧“需要向你说明的一件事”写的是：安装 jsdom 时，npm 找到了用户主目录的 `package.json`，修改了依赖，将 pnpm 管理的部分符号链接拉平成真实目录；Agent 自述已经恢复 `package.json`，仍留下目录及锁文件需要收尾。这超出了“某项测试依赖安装失败”的含义。截图只能证明 Agent 作出了这份报告，无法独立证明本机文件当时的真实状态；但已经足以否定文章对本次过程的无风险保证。

**可直接替换的正文**：

> 需要你点头时，先看清它准备操作哪个目录、是否安装依赖、是否改动已有文件。不确定就让它解释后再继续。这次实操也出了一个小插曲：Agent 报告，安装测试依赖时误动了用户主目录，并留下需要收尾的文件。页面做出来了，过程仍要复核，这也是第一次练习应该使用独立目录、保持默认权限的原因。

**可直接替换的 alt**：

> WorkBuddy 左侧列出交付与验证说明，并报告安装 jsdom 时误改用户主目录及残留文件；右侧为待办清单预览，显示四项待办、两项未完成。

**处理边界**：本项建议补足说明和纠正 alt，不建议删除现有截图，也不推断误操作一定由某一个权限开关造成。

### A02：默认权限并非每次文件修改、每条命令都重新确认

**原句摘录（第 52、89、128、130 行）**：“它每动一次文件、每跑一条命令都会先问你一句”；“涉及文件修改……都会先征求你的同意”；“目录就是它的活动范围”。

**问题**：当前官方说明允许工作空间内的普通文件操作直接执行，敏感路径、越界或高风险动作按规则确认。文章还遗漏了一个重要范围：完全访问开关影响当前客户端内的已有及新建任务，不只是眼前这一单。选定目录也不能被讲成任何权限状态下都无法突破的硬隔离。

**可直接替换**：

> 输入框底部可以查看权限状态。第一次练习保持默认权限：工作空间内的普通操作可能直接执行，遇到越界或高风险动作时会请求确认，不是每改一个文件都重新问。完全访问会减少确认，并影响当前客户端里的所有任务，练习时先别开。独立目录能收窄任务范围，重要文件仍需另行备份。

第 52、89、128、130 行应统一口径，删除第 52 行对打开完全访问的随口鼓励。依据：[WorkBuddy 默认权限与安全沙箱](https://www.workbuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Permission-Modes)。

第 64 行若保留个人经历，应改为“在我这台 Windows 电脑上，两版按默认方式安装时会覆盖”，不再写成普遍限制。依据：[WorkBuddy 新建任务栏](https://www.workbuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Task-Bar)。

### A04：第一条提示词缺少操作边界，环境异常时没有停止条件

**原句摘录（第 46、71—76、130 行）**：“随手起个名字，比如‘1’”；“用 Node 起一个本地服务器”；独立空目录和备份提醒直到展开篇才出现。

不能据此断言 WorkBuddy 不内置 Node，或每个新用户都需要手动安装。真正需要补的是使用哪个运行环境、缺失时如何降级，以及什么情况下应该暂停。

**可直接前置到第 2 步**：

> 为这次练习新建一个独立空文件夹，只放练习产物，不要选已有项目或用户主目录。发送前确认任务指向这个文件夹，并保持默认权限。

**可直接补入提示词**：

> 只在当前工作空间创建本次应用和必要的验证文件，不修改已有文件、上级目录或全局配置，不安装额外依赖。先检查已有验证环境；如果缺少工具，先报告缺什么以及替代办法，等我确认后继续。

这是操作约束，不能代替客户端权限控制；也不要再向读者保证加上这段就绝不会越界。

### A05：验收覆盖不完整，服务器验证和双击使用没有对齐

**原句摘录（第 72—76、93、97 行）**：“双击就能在浏览器打开”；“数据存 localStorage，刷新不丢”；“会直接把做好的页面给你打开”。

**问题**：第 6 步只问添加、筛选、刷新、计数，遗漏删除、创建时间、清除已完成以及不误删未完成项。截图列出的验证证据是 HTTP 响应、内容标记和文件一致性，不能单独证明所有交互都正常；右侧是客户端内的预览，也不能证明每次都会自动拉起外部浏览器。

另有技术边界：`file:` 直接打开与 HTTP 服务是不同的使用入口，localStorage 的 `file:` 行为没有统一保证。不能用 HTTP 下的检查替代“双击打开”这项验收。本次未取得生成的实际 HTML，无法复跑其功能，不能判定应用本身有 bug。依据：[MDN localStorage 的来源与 file URL 限制](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)、[WorkBuddy 结果查看](https://www.workbuddy.cn/docs/workbuddy/Results)。

**可直接替换第 6 步的检查说明**：

> 在产物卡片或右侧预览中打开页面；没有自动打开，就找到交付的 HTML 文件，按前面约定的方式打开。先添加两条不同的待办，核对创建时间；勾选其中一条，检查未完成数和三个筛选项；再删除一条待办，检查计数；刷新同一个页面，确认内容和状态保留；最后清除已完成项，确认未完成项没有被删除。

**补充一句**：

> 如果承诺双击使用，就再双击交付文件检查一次，并记下测试所用浏览器；在预览、本地网址和文件之间切换时，原先的本地存储数据不一定共享。

### A06：计费公式缺少依据，模型倍率高低也概括错了

**原句摘录（第 107、139 行）**：“这类旗舰模型倍率高（0.43x），日常问答、文案类模型倍率低”；“文件处理按大小、自动化任务按次扣”。

**问题**：截图中还有 0.59x、1.33x、6.67x 等倍率，不能仅凭“旗舰”二字把 0.43x 归为高倍率，也不能由任务叫问答还是文案推导其使用模型的倍率。当前官方积分页按模型 Token 单价及任务复杂度解释消耗，没有核到文中那两条固定扣分公式。

**可直接替换**：

> WorkBuddy 用积分衡量资源消耗，订阅套餐按周期提供积分。实际消耗与所选模型和任务处理量有关，不能只看任务名称；余额、倍率和明细以客户端为准。API 则是另一种接入与计费方式，按对应平台的用量规则结算。

依据：[WorkBuddy 积分说明](https://www.workbuddy.cn/docs/workbuddy/Credits)、[官方定价](https://www.workbuddy.cn/docs/workbuddy/Pricing)。文中“赠送积分常见到账后一个月有效”的方向可保留，官方目前确有对应说明。
